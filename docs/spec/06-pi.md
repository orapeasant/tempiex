# 06 — Pi: Agent Harness Specification

## Overview

**Component**: Tempiex Pi — Agent Harness  
**Folder**: `pi/`  
**Language**: Go 1.24+  
**Type**: Edge Agent Daemon + Tempiex Worker  
**Implementation Priority**: 6 — Depends on tempiex (SDK + gRPC), server (HTTP API)

## Purpose

`pi` is a lightweight Go daemon designed to run on resource-constrained devices (Raspberry Pi, any Linux edge node, Docker container) or on any host that needs to execute Tempiex workflow activities as a managed, observable agent harness.

**Inspired by [badlogic/pi-mono](https://github.com/badlogic/pi-mono)** (a TypeScript stateful agent harness with event streaming, tool execution, and session management), `pi` reimplements the same patterns in Go for the Tempiex ecosystem:

- **Tempiex Worker** — polls one or more task queues; executes workflow activities
- **Tool execution** — activity implementations are registered as typed tools with before/after hooks
- **Event streaming** — emits structured events for every tool start, update, end, and error
- **Session management** — tracks active runs, persists state across restarts
- **Server API** — HTTP/WebSocket endpoint for the web UI to inspect and control live runs
- **OTel observability** — traces, metrics, and logs forwarded to the OTel collector
- **Graceful shutdown** — drains in-flight activities before exit

## Core Concepts

### Tool

A `Tool` is a typed activity implementation:

```go
type Tool[I, O any] struct {
    Name        string
    Description string
    // Activity function — this is registered with the Tempiex worker
    Execute func(ctx context.Context, input I) (O, error)
    // Optional: called before Execute; can block or annotate
    BeforeExec func(ctx context.Context, input I) error
    // Optional: called after Execute; can transform output
    AfterExec  func(ctx context.Context, input I, output O, err error) (O, error)
    // ExecutionMode: "parallel" or "sequential" within a workflow task
    ExecutionMode string
}
```

### Event

Every tool execution emits structured events to the event bus:

```go
type EventType string

const (
    EventExecutionStart  EventType = "execution_start"
    EventExecutionUpdate EventType = "execution_update"  // streaming progress
    EventExecutionEnd    EventType = "execution_end"
    EventExecutionError  EventType = "execution_error"
)

type Event struct {
    ID          string
    Type        EventType
    SessionID   string
    RunID       string
    WorkflowID  string
    ToolName    string
    ToolCallID  string
    Timestamp   time.Time
    Payload     any    // tool-specific data (serialized as JSON)
    Error       string // non-empty on error events
}
```

### Session

A session corresponds to a Tempiex workflow execution being tracked by this pi instance:

```go
type Session struct {
    ID          string
    WorkflowID  string
    RunID       string
    Namespace   string
    TaskQueue   string
    Status      SessionStatus   // active | completed | failed | cancelled
    StartedAt   time.Time
    EndedAt     *time.Time
    Events      []Event
    Tools       []string        // tools used during this session
}

type SessionStatus string

const (
    SessionActive    SessionStatus = "active"
    SessionCompleted SessionStatus = "completed"
    SessionFailed    SessionStatus = "failed"
    SessionCancelled SessionStatus = "cancelled"
)
```

### Event Flow

When a Tempiex activity is dispatched to a `pi` worker:

```
Tempiex schedules activity on task queue
│
▼ pi worker polls → dequeues task
│
├─ event: execution_start { toolName, args, workflowID, runID }
│
├─ BeforeExec hook (optional; can block)
│
├─ Execute(ctx, input)
│   ├─ tool may emit progress via ctx streaming helper
│   │   → event: execution_update { partial result }
│   └─ returns (output, error)
│
├─ AfterExec hook (optional; can transform result)
│
├─ event: execution_end   { output }
│  or
└─ event: execution_error { error message }
    │
    └─ activity returns error → Tempiex retries per retry policy
```

```yaml
# pi/config/development.yaml

tempiex:
  address: "localhost:8133"   # tempiex or proxy address
  namespace: "default"
  tls:
    enabled: false
  apiKey: ""

workers:
  - taskQueue: "pi-default"
    maxConcurrentActivities: 10
    maxConcurrentWorkflowTasks: 5
  # additional task queues:
  # - taskQueue: "pi-shell"
  #   maxConcurrentActivities: 4

api:
  host: "0.0.0.0"
  port: 8090
  corsOrigins:
    - "http://localhost:8080"

session:
  storePath: "./pi-sessions.db"
  maxCompletedSessions: 1000

metrics:
  otel:
    endpoint: "localhost:4317"
    insecure: true

log:
  level: "info"
  format: "json"
```

All values override via env with `PI_` prefix: `PI_TEMPIEX_ADDRESS`, `PI_API_PORT`, etc.


## Tool SDK (public API)

Users register their own tools:

```go
package main

import (
    "context"
    "github.com/tempiex/pi/internal/tool"
    "github.com/tempiex/pi/internal/agent"
)

type ShellInput struct {
    Cmd string `json:"cmd"`
}

type ShellOutput struct {
    Stdout   string `json:"stdout"`
    Stderr   string `json:"stderr"`
    ExitCode int    `json:"exitCode"`
}

func main() {
    registry := tool.NewRegistry()

    registry.Register(tool.Tool[ShellInput, ShellOutput]{
        Name:        "shell",
        Description: "Execute a shell command",
        Execute: func(ctx context.Context, input ShellInput) (ShellOutput, error) {
            // ... exec.CommandContext(ctx, "sh", "-c", input.Cmd)
        },
        BeforeExec: func(ctx context.Context, input ShellInput) error {
            // validate or block dangerous commands
            return nil
        },
    })

    ag := agent.New(agent.Options{
        Registry:  registry,
        TaskQueue: "pi-default",
    })
    ag.Run(context.Background())
}
```

## Built-in Tools

| Tool | Name | Description |
|------|------|-------------|
| Shell | `shell` | Execute shell commands with stdout/stderr streaming |
| HTTP | `http_request` | Make HTTP requests with configurable method, headers, body |
| File Read | `file_read` | Read file contents |
| File Write | `file_write` | Write content to a file |

Built-in tools are optional — register only what you need.

## Graceful Shutdown

On `SIGINT`/`SIGTERM`:
1. Stop accepting new activities from task queues.
2. Wait for in-flight activities to complete (up to `shutdownTimeout`, default 30s).
3. Flush pending events to session store.
4. Close HTTP server.
5. Exit 0.

## Observability

### Metrics (OTel OTLP)

| Metric | Type | Description |
|--------|------|-------------|
| `pi.activity.executions.total` | Counter | by tool_name, status (success/error) |
| `pi.activity.duration` | Histogram | by tool_name |
| `pi.sessions.active` | Gauge | current active sessions |
| `pi.worker.poll.latency` | Histogram | by task_queue |

### Traces

- Each activity execution creates a span child of the Tempiex workflow trace context.
- Tool `BeforeExec` and `AfterExec` create sub-spans.

### Logs

zerolog JSON to stdout. Fields: `level`, `ts`, `session_id`, `workflow_id`, `run_id`, `tool`, `msg`.

## Differences from badlogic/pi-mono

| Concern | pi-mono (TypeScript) | tempiex/pi (Go) |
|---------|---------------------|-----------------|
| Agent loop | LLM-driven multi-turn | Tempiex activity worker |
| Tool execution | LLM calls tools | Tempiex schedules activities |
| Event streaming | in-process SSE | in-process SSE via http.Flusher |
| Session persistence | SQLite via node:sqlite | SQLite via modernc.org/sqlite |
| Retry / durability | manual retry in agent | Tempiex retry policies |
| Parallelism | configurable per tool | Tempiex concurrent activity slots |
| Observability | in-process events | OTel OTLP + Tempiex metrics |

The structural patterns (Tool, Event, Session, EventBus, SSE streaming, BeforeExec/AfterExec hooks) are directly inspired by pi-mono's `@earendil-works/pi-agent-core` and `@earendil-works/pi-server` packages, adapted to Go idioms and the Tempiex execution model.
